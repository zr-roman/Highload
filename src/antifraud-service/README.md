# Антифрод (Python)

Проверка платежа после авторизации в банке: пропустить или отклонить. Payments.Api вызывает его на синхронном пути платежа, поэтому главное здесь — бюджет задержки и поведение при сбоях. Отказ антифрода отменяет авторизацию в банке — это сага этапа 4.

Python 3.12, FastAPI + uvicorn, Pydantic, `redis.asyncio`; тесты — pytest, линтер — ruff, зависимости — uv.

## API

**`POST /v1/checks`**

```json
{"paymentId": "0192f0c8-0000-7000-8000-000000000001", "merchantId": 42, "amount": 150000, "currency": "RUB", "createdAt": "2026-10-28T12:00:00Z"}
```

```json
{"paymentId": "0192f0c8-0000-7000-8000-000000000001", "decision": "allow", "score": 0.0, "reasons": [], "modelVersion": "rules-2"}
```

`decision` — `allow` или `deny`; `score` — риск от 0 до 1; `reasons` — коды сработавших правил; `modelVersion` — какие правила или модель приняли решение. Сумма — в копейках, `createdAt` — обязательно со смещением.

Крупный продавец — тот, у кого в Payments.Api своя квота лимита запросов, — приходит со своим классом и квотой:

```json
{"paymentId": "...", "merchantId": 1, "amount": 150000, "currency": "RUB", "createdAt": "2026-10-28T12:00:00Z", "merchantClass": "large", "quotaPerSecond": 1000}
```

`merchantClass` — `standard` (по умолчанию) или `large`; `quotaPerSecond` обязателен для `large` и запрещён для `standard`. Квоты хранятся только в Payments.Api, здесь они не дублируются.

Проверка идемпотентна по `paymentId`: решение хранится в Redis, и повтор получает его как есть, даже если правила теперь ответили бы иначе. Поэтому Payments.Api может безопасно повторять запрос после таймаута.

Ошибки — с телом `{"error": "..."}`, как у эмулятора банка:

- 400 — неверный запрос, ошибка на стороне Payments.Api;
- 503 — Redis недоступен или не ответил за `ANTIFRAUD_REDIS_TIMEOUT_MS`. Без Redis нет ни сохранённого решения, ни счётчика, поэтому ответу доверять нельзя. Для Payments.Api это «исход неизвестен».

**`GET /healthz`** — 200 и `ok`.

## Правило частоты

Не больше N платежей одного продавца за окно, иначе `deny` с причиной `velocity`.

- **Лимит.** Обычный продавец — `ANTIFRAUD_VELOCITY_LIMIT` за `ANTIFRAUD_VELOCITY_WINDOW_SECONDS`. Крупный — квота × длина окна: правило не режет темп, который пропускает лимитер Payments.Api. Нулевой лимит отклоняет всё — так проверяется отмена авторизации.
- **Окно** фиксированное, по `createdAt` платежа, а не по времени проверки. Платежи, которые ждали перепроверки, пока антифрод лежал, считаются в своих окнах и не сваливаются в текущее. На стыке окон пройдёт до двух лимитов — для первого правила допустимо.
- **Один платёж — одно увеличение счётчика.** Lua-скрипт за один шаг ставит платежу отметку с его номером в окне и увеличивает счётчик. Дубль, который не застал сохранённого решения, получает тот же номер и ничего не добавляет. Поэтому решение по платежу не зависит от того, сколько раз его проверили.
- **Ключи:** `af:velocity:{merchantId}:{номер окна}` — счётчик, `af:counted:{paymentId}` — отметка; живут два окна. Решение — `af:decision:{paymentId}`, живёт `ANTIFRAUD_DECISION_TTL_SECONDS`.

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ANTIFRAUD_REDIS_URL` | `redis://127.0.0.1:6379/0` | Redis для счётчиков и сохранённых решений |
| `ANTIFRAUD_VELOCITY_LIMIT` | 100 | не больше стольких платежей одного обычного продавца… |
| `ANTIFRAUD_VELOCITY_WINDOW_SECONDS` | 60 | …за такое окно |
| `ANTIFRAUD_DECISION_TTL_SECONDS` | 86400 | сколько хранится решение для повторов |
| `ANTIFRAUD_REDIS_TIMEOUT_MS` | 20 | Redis, не ответивший за это время, считается недоступным: ответ 503. Попытка Payments.Api — 50 мс |

Неверное значение — сервис не стартует.

## Запуск

Один раз — uv (он же поставит Python 3.12):

```powershell
winget install --id=astral-sh.uv -e
```

Redis поднимается вместе с Kafka: `docker compose up -d` в корне репозитория.

```powershell
cd src\antifraud-service
uv sync
uv run uvicorn antifraud.main:app --host 127.0.0.1 --port 5400 --workers 4
```

`--workers` — несколько процессов: из-за GIL один процесс Python занимает одно ядро.

Проверка:

```powershell
$body = '{"paymentId":"0192f0c8-0000-7000-8000-000000000001","merchantId":42,"amount":150000,"currency":"RUB","createdAt":"2026-10-28T12:00:00Z"}'
Invoke-RestMethod -Method Post -Uri http://localhost:5400/v1/checks -ContentType "application/json" -Body $body
```

## Тесты и линтер

```powershell
uv run pytest
uv run ruff check .
uv run ruff format .
```

Тестам не нужен запущенный Redis: вместо него — fakeredis, Redis в памяти с тем же API. Lua-скрипты он выполняет через lupa — её ставит `fakeredis[lua]` из dev-зависимостей.

## Структура

- `antifraud/main.py` — приложение FastAPI, маршруты, Redis и настройки на старте процесса, ответы 400 и 503.
- `antifraud/models.py` — контракт: запрос и ответ, JSON в camelCase.
- `antifraud/checker.py` — решение по платежу: идемпотентность по `paymentId` и правила.
- `antifraud/velocity.py` — правило частоты: лимит по классу продавца, окно, Lua-скрипт счётчика.
- `antifraud/features.py` — признаки платежа, общие для сервиса и обучения модели.
- `antifraud/settings.py` — настройки из переменных окружения.
- `tests/conftest.py` — общие фикстуры: настройки, Redis в памяти, приложение с подменённым Redis.
- `tests/test_api.py` — контракт через HTTP: ответ в camelCase, повтор, 400 на неверный запрос, 503 без Redis.
- `tests/test_checker.py` — идемпотентность: повтор, одновременные дубли, срок хранения решения.
- `tests/test_velocity.py` — правило частоты: лимиты обычного и крупного продавца, дубли, окна.
- `tests/test_settings.py` — значения по умолчанию и отказ стартовать с неверными.
