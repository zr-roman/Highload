# Эмулятор банка (Go)

Банк-эквайер, к которому Payments.Api будет обращаться по сети вместо `FakeAcquirer` внутри процесса. Эмулятор отвечает с задержкой и умеет сбоить с заданной частотой: на нём Payments.Api отрабатывает таймауты, ретраи, circuit breaker и восстановление платежей, ответ по которым не дошёл.

Только стандартная библиотека Go 1.24: `net/http` с маршрутами по методу и пути, `log/slog`, `context`.

## API

**`POST /v1/authorizations`** — решение по платежу.

```json
{"paymentId": "0192f0c8-0000-7000-8000-000000000001", "merchantId": 42, "amount": 150000, "currency": "RUB"}
```

```json
{"paymentId": "0192f0c8-0000-7000-8000-000000000001", "status": "approved", "authorizationCode": "798041", "decidedAt": "2026-10-21T20:09:32.287Z"}
```

`status` — `approved`, `declined` или `voided`; код авторизации есть только у одобренных. Сумма — в копейках.

**`GET /v1/authorizations/{paymentId}`** — уже принятое решение: 200 с тем же JSON или 404, если решения нет. По нему клиент узнаёт исход платежа, ответ на который до него не дошёл.

**`POST /v1/authorizations/{paymentId}/void`** — отмена одобренной авторизации: банк снимает холд с денег покупателя. Тела нет. Payments.Api вызывает её, когда антифрод отклонил платёж уже после банка (сага этапа 4).

```json
{"paymentId": "0192f0c8-0000-7000-8000-000000000001", "status": "voided", "authorizationCode": "798041", "decidedAt": "2026-10-21T20:09:32.287Z", "voidedAt": "2026-10-21T20:09:32.401Z"}
```

| Решение в банке | Ответ |
|---|---|
| approved | 200, статус становится `voided`, появляется `voidedAt`; код и `decidedAt` остаются |
| voided | 200, тот же ответ, что в первый раз, с тем же `voidedAt` |
| declined | 409: отменять нечего |
| нет решения | 404 |

После отмены `GET` и повторная авторизация с тем же `paymentId` возвращают `voided`: снова одобрить платёж повтор не может.

**`GET /healthz`** — 200 и `ok`.

| Код | Когда |
|---|---|
| 200 | решение принято сейчас или раньше |
| 400 | не JSON или неверные поля: пустой `paymentId`, `merchantId` или `amount` ≤ 0, `currency` не из трёх символов |
| 404 | `GET` и void: решения по этому платежу нет |
| 409 | авторизация: этот `paymentId` уже приходил с другими полями; void: платёж отклонён |
| 500 | имитация сбоя до решения или до отмены |

## Поведение

**Идемпотентность по `paymentId`.** Повторный запрос с тем же `paymentId` получает то же решение, поэтому клиенту безопасно повторять запросы. Тот же `paymentId` с другими полями — ошибка клиента, 409; сохранённое решение при этом не меняется. Проверка, решение и запись выполняются под одним мьютексом, так что два одновременных запроса с одним `paymentId` получают одно решение.

**Три вида сбоев — три разных случая для клиента:**

| Сбой | Что происходит | Что видит `GET` потом | Что делать клиенту |
|---|---|---|---|
| Ошибка до решения (`BANK_ERROR_PERCENT`) | 500 сразу, решения нет | 404 | повторить запрос |
| Поздний ответ (`BANK_SLOW_PERCENT`) | решение принято и сохранено, ответ задерживается на `BANK_SLOW_MS` | 200 с решением | не списывать второй раз: повтор с тем же `paymentId` вернёт сохранённое решение |
| Клиент ушёл во время обработки | банк прекращает работу над запросом и ничего не решает | 404 | повторить запрос |

Поздний ответ — самый опасный случай: клиент получил таймаут и не знает исхода. Без идемпотентности банка повтор превратился бы в двойное списание.

**Сбои у отмены — те же.** `BANK_ERROR_PERCENT`, `BANK_ERROR_MERCHANT`, задержка обработки и `BANK_SLOW_PERCENT` действуют и на void: 500 до отмены ничего не отменяет, ушедший клиент — тоже, а поздний ответ приходит, когда отмена уже записана. Продавца отмены банк берёт из сохранённого запроса авторизации. Повторять void безопасно: отмена идемпотентна.

**Упрощение: void после списания не моделируется.** В настоящем банке отменить можно только авторизацию, деньги по которой ещё не списаны; после списания нужен возврат (refund). У эмулятора списания нет: captured — статус только в Payments.Api.

**Решения хранятся в памяти.** После перезапуска эмулятор их забывает, и void ранее одобренного платежа получит 404.

**Сбой у одного продавца** (`BANK_ERROR_MERCHANT`). Банк отвечает 500 на каждую авторизацию и отмену этого продавца, остальных обслуживает как обычно. Для клиента это та же ошибка до решения, только повтор не поможет, пока сбой не кончится. На нём проверяется, что отказы одного продавца не открывают circuit breaker Payments.Api для всех (этап 3, шаг 6).

## Настройки

Переменные окружения; неверное значение — ошибка при старте.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `BANK_ADDR` | `:5300` | адрес и порт |
| `BANK_LATENCY_MS` | 50 | время обработки платежа |
| `BANK_JITTER_MS` | 20 | к нему добавляется случайная часть до стольких миллисекунд |
| `BANK_DECLINE_PERCENT` | 2 | доля отклонённых платежей |
| `BANK_ERROR_PERCENT` | 0 | доля ответов 500 до решения или отмены |
| `BANK_SLOW_PERCENT` | 0 | доля поздних ответов, у авторизации и у отмены |
| `BANK_SLOW_MS` | 5000 | на сколько задерживается поздний ответ |
| `BANK_ERROR_MERCHANT` | 0 | продавец, каждая авторизация и отмена которого получает 500; 0 — такого нет |

## Запуск

```powershell
cd src\bank-emulator
go run .
```

Во втором окне:

```powershell
$body = '{"paymentId":"0192f0c8-0000-7000-8000-000000000001","merchantId":42,"amount":150000,"currency":"RUB"}'
Invoke-RestMethod -Method Post -Uri http://localhost:5300/v1/authorizations -ContentType "application/json" -Body $body
Invoke-RestMethod http://localhost:5300/v1/authorizations/0192f0c8-0000-7000-8000-000000000001
```

Ненадёжный банк: 10 % отказов и 5 % поздних ответов.

```powershell
$env:BANK_ERROR_PERCENT = "10"
$env:BANK_SLOW_PERCENT = "5"
go run .
```

Ctrl+C останавливает сервер аккуратно: он перестаёт принимать соединения и дожидается запросов в работе.

## Тесты

```powershell
go test ./...
go vet ./...
```

- `bank_test.go` — логика банка: одобрение и отказ, повтор, конфликт, `Get`, одно решение на конкурентные запросы, вероятности и задержка; отмена — четыре исхода, `Get` и повторная авторизация после неё, одна отмена на конкурентные запросы. Случайность в тестах подменяется фиксированным значением.
- `handlers_test.go` — HTTP через `httptest`: коды ответов и валидация, а главное — три вида сбоев и сбой у одного продавца. Тесты проверяют, что после ошибки и после ушедшего клиента решения нет, а при позднем ответе решение уже видно через `GET`, пока сам ответ ещё не пришёл. Те же проверки — для отмены, плюс 200, 404 и 409.
- `config_test.go` — значения по умолчанию, чтение переменных окружения, отказ на неверных значениях.

`go test -race ./...` дополнительно ищет гонки данных; на Windows ему нужен компилятор C (gcc).
