# Kafka в кластере: Strimzi и отказ брокера

Kafka стенда переехала из одного StatefulSet в кластер из трёх узлов под управлением оператора Strimzi. Главный вопрос этапа: что станет с платежами, которые ещё не дошли до Ledger, когда умрёт нода с брокером. Ответ, измеренный в шести прогонах: **платежи не теряются, а асинхронная доставка в Ledger встаёт примерно на 20 секунд**. Чтобы прийти к этому, пришлось найти и исправить три проблемы, и ни одна из них не была в самой Kafka. Опыты с отказом PostgreSQL — в [postgres-failover.md](postgres-failover.md), инструмент опытов — [load/Failover](../load/Failover).

## Как устроено

```
 Payments.Api ── outbox (PostgreSQL) ── OutboxRelay ──► kafka-kafka-bootstrap:9092 ──► Ledger.Service
                                        (один лидер,        │
                                         advisory-lock)     ├─ kafka-broker-0  (agent-1)   брокер + контроллер KRaft
                                                            ├─ kafka-broker-1  (agent-0)   брокер + контроллер KRaft
                                                            └─ kafka-broker-2  (server-0)  брокер + контроллер KRaft

 payments.captured: 8 партиций × 3 реплики, min.insync.replicas 2, продюсер acks=all + идемпотентность
```

## Решения и почему

| Решение | Почему |
|---|---|
| Оператор Strimzi, а не свой StatefulSet | Как CloudNativePG для PostgreSQL: оператор перекатывает брокеры по одному и только когда все партиции остаются в ISR на остальных, топики хранятся как ресурсы `KafkaTopic` в git |
| Три узла, каждый одновременно брокер и контроллер KRaft | Кворум из трёх контроллеров и три реплики партиции переживают потерю любой ноды. Отдельные контроллеры — ещё три JVM, ноутбук их не вмещает |
| Один брокер на ноду (`podAntiAffinity: required`) | Отказ ноды забирает одну реплику партиции, никогда две |
| `min.insync.replicas 2` и `acks=all` у продюсера | Запись подтверждается, только когда она есть на двух брокерах, и только после этого строка outbox удаляется. Один брокер лежит — запись идёт. Два — продюсеру отказывают, платежи ждут в outbox. Тот же выбор, что `dataDurability: required` у PostgreSQL |
| Топик `payments.captured` объявлен как `KafkaTopic` | Его репликация записана в git. Сервисы по-прежнему вызывают `CreateTopics` при старте, теперь с коэффициентом репликации брокера по умолчанию (`-1`), а не 1 |
| NetworkPolicy делает Strimzi (`networkPolicyPeers`) | Порт 9092 открыт для payments-api, ledger-service, самих брокеров и пода замеров `kafka-probe`, порты между брокерами — для брокеров и оператора |
| Strimzi с провайдером `restricted` | Иначе поды брокеров по профилю baseline, и namespace с Pod Security `restricted` их не пустит |

## Прогоны

Каждый раз останавливалась agent-нода с брокером, у которого были лидеры партиций, и с лидером OutboxRelay. Основной PostgreSQL оставался на `server-0`, чтобы отказ Kafka не смешивался с failover базы. Нагрузка 50 платежей в секунду, нода лежит 90 секунд.

| | 0: `node-failure.ps1` | 1: Failover | 2: Failover | 3: Failover |
|---|---|---|---|---|
| Что изменено перед прогоном | — | keepalive в PostgreSQL | одиночные сервисы убраны с ноды, замеры Kafka в своём поде | проверка топика не держит outbox |
| Ошибки у клиента | 57 из 7 470 (0,76 %) | 5 994 из 7 500 (80 %) | 57 из 7 445 (0,77 %) | 67 из 7 427 (0,90 %) |
| Outbox: наибольшее ожидание | 115 с | 94 с | 40 с | **21 с** |
| Outbox: строк, наибольшее | 5 559 | 16 | 1 864 | 928 |
| Платежей в базе / успешных ответов | инварианты сходятся | 1 516 / 1 506 | 7 402 / 7 388 | 7 374 / 7 360 |
| Наименьший ISR | 2 | 1 — упал второй брокер | 2 | 2 |

Прогоны 4 и 5 — не остановка ноды, а обрыв сети (`--mode partition`): ниже, отдельным разделом.

Потерь не было ни разу: число платежей в базе не меньше числа успешных ответов, инварианты Ledger сходятся, после возвращения ноды все партиции вернулись в полный ISR, а Ledger догнал. Менялось только время, на которое вставала доставка в Ledger.

**Прогон 0: блокировка мёртвого лидера.** Kafka отработала как надо: лидеры партиций сменились, ISR сократился до двух, запись не останавливалась. А outbox простоял до возвращения ноды. OutboxRelay и восстановление платежей работают в одном экземпляре, лидерство держится на сессионной advisory-блокировке PostgreSQL. Под-лидер умер вместе с нодой, но его соединение никто не закрыл: мёртвая нода не может послать ни FIN, ни RST. PostgreSQL считал сессию живой, второй экземпляр ждал лидерства 7 минут 20 секунд и получил его, только когда kubelet вернувшейся ноды убил старый контейнер. Без возвращения ноды он ждал бы до двух часов — столько по умолчанию в Linux ждёт TCP keepalive. Исправление — keepalive на стороне сервера (`tcp_keepalives_idle 10`, `interval 5`, `count 3` в [postgres.yaml](../deploy/k8s/postgres.yaml)): мёртвый клиент обнаруживается за ~25 секунд, сессия закрывается вместе с блокировками.

**Прогон 1: Traefik и упавший второй брокер.** 80 % ошибок с медианой 3 мс: единственная копия Traefik стояла на останавливаемой ноде, вместе с ней пропал вход в кластер. А outbox стоял потому, что во время отказа **перезапустился брокер 2**, лидер кворума KRaft. Вернувшись, он падал с `IllegalStateException: Cannot transition to Follower with leader 2 and epoch 1 since it matches the local node.id` — пытался стать последователем самого себя. Это сценарий, описанный в KAFKA-16281. Пока лидерство кворума не перешло к брокеру 1, живой оставалась одна реплика, а при `min.insync.replicas 2` Kafka в одну копию не пишет. Брокер 2 упал ровно тогда, когда закончился замер Kafka, а замер запускал две JVM инструментов Kafka прямо в контейнере брокера, в его лимите памяти. Замеры перенесены в отдельный под, после этого второй брокер не падал ни разу.

**Прогон 2: проверка топика.** Новый лидер outbox перед первой пачкой проверяет топик запросом `CreateTopics`. Запрос ушёл контроллеру из закешированных метаданных — брокеру на мёртвой ноде — и падал по таймауту 5 секунд раз за разом: `Outbox relay failed … Local: Timed out`, пауза секунда, снова. У партиций к этому времени уже были живые лидеры: по логам брокера 1, Kafka исключила брокер 0 и переназначила его партиции через 8 секунд после остановки. 40 секунд outbox ждал служебную проверку, которая для отправки не нужна.

**Прогон 3: после исправления.** Проверка топика теперь одна попытка без ожидания результата: если не ответила — `publishing anyway`, пачка уходит. Если топика правда нет, продюсер получит `UnknownTopicOrPart`, проверка взведётся снова и создаст топик перед следующей попыткой. По логам нового лидера: одна неудачная проверка (`Failed while waiting for controller: Local: Timed out`), сразу отправка, ни одной ошибки отправки.

## Обрыв сети: проверка keepalive

`docker stop` — аккуратный отказ: процессы на ноде получают сигнал и закрывают свои соединения, и партнёры узнают об этом сразу. Так не умирает машина, у которой пропало питание или сеть: соединения с ней просто замолкают. Режим `--mode partition` отключает ноду от сети k3d (`docker network disconnect`), не останавливая её: всё на ней работает, но ни один пакет не уходит и не приходит, ничего не закрывается. Именно для этого случая в PostgreSQL включён keepalive.

| | Прогон 3: `docker stop` | Прогон 4: обрыв сети | Прогон 5: обрыв сети, таймауты клиентов 10 с |
|---|---|---|---|
| Лидерство outbox перешло | через 6 с | **через 18 с** — keepalive закрыл сессию мёртвого пода | через 19 с |
| Outbox: наибольшее ожидание | 21 с | 33 с (в повторе того же прогона — 82 с) | **31 с** |
| Отставание Ledger, наибольшее | 59 сообщений | **2 578 сообщений** (в повторе — 4 040) | **45 сообщений** |
| Ошибки у клиента | 0,90 % | 4,92 % | 2,40 % |
| Платежей в базе / успешных ответов | 7 374 / 7 360 | 7 049 / 7 014 | 7 158 / 7 125 |

**Keepalive работает.** В прогоне 0, без keepalive, второй экземпляр получил лидерство outbox только после возвращения ноды. С keepalive — через 18 секунд обрыва: PostgreSQL не дождался ответа на пробы, закрыл сессию отрезанного пода и снял его блокировки.

**Ledger почти минуту не читал.** Координатором группы `ledger` был брокер на отрезанной ноде. Консьюмер слал ему heartbeat и 45 секунд ждал ответа — столько по умолчанию `session.timeout.ms`, — потом сдал все партиции и вступил в группу заново (`SESSTMOUT … after 45160 ms without a successful response from the group coordinator`). При `docker stop` соединение с координатором закрывалось, и консьюмер сразу искал нового. Тот же класс проблемы, что с блокировкой outbox: молчащий партнёр держит клиента до таймаута. `session.timeout.ms` у Ledger сокращён до 10 секунд, heartbeat — раз в 3 секунды (`PaymentsConsumer`).

**Продюсер outbox ждал отрезанный брокер минуту.** В повторе прогона 4 outbox ждал 82 секунды, хотя новый лидер outbox появился через 21. Запросы, отправленные брокеру 0 до обрыва, висели до таймаута librdkafka `socket.timeout.ms` — 60 секунд по умолчанию (`Timed out ProduceRequest in flight (after 60080ms)`), а идемпотентный продюсер не шлёт новых сообщений в партицию, пока не решилась судьба отправленных: иначе нарушится порядок. `OutboxRelay` ждёт всю пачку, и три зависшие партиции держали отправку целиком. К тому же отрезанный брокер был контроллером KRaft: новый контроллер появился через ~40 секунд, и только через 10 секунд после этого брокер 0 исключён. `socket.timeout.ms` у продюсера сокращён до 10 секунд (`Program.cs`): зависший запрос отменяется, продюсер шлёт в нового лидера, идемпотентность не даёт повтору записать дважды.

**Прогон 5 — оба таймаута сокращены.** Outbox ждал 31 секунду вместо 82 и опустел через 13 секунд после смены лидера outbox, пока нода ещё была отрезана. Ledger отстал на 45 сообщений вместо 2 578–4 040: консьюмер находит нового координатора за 10 секунд, а не за 45.

**Ограничение стенда.** После `docker network connect` нода снова `Ready`, но сеть между её подами и подами других нод не восстановилась: брокер на ней не вернулся в ISR, копия CoreDNS на ней не отвечала остальным, и DNS в кластере работал через раз. Помог перезапуск контейнера ноды: k3s при старте заново настраивает flannel. Это свойство k3d, а не Kubernetes, и `load/Failover` в режиме `partition` теперь перезапускает ноду после возвращения в сеть. Сам обрыв при этом остаётся честным: всё, что меряет прогон, происходит до возвращения.

## Из чего состоят 21 секунда

| Отрезок | ≈ | Что можно сделать |
|---|---|---|
| Второй экземпляр берёт лидерство outbox: блокировку он пробует раз в 5 секунд | 6 с | Пробовать чаще — больше запросов к базе от ждущих экземпляров |
| Kafka исключает брокер и переназначает его партиции, продюсер ждёт | ~8 с | Уменьшить `broker.session.timeout.ms` — на перегруженной машине Kafka начнёт исключать живые брокеры |
| Одна проверка топика с таймаутом 5 секунд | ~5 с | Таймаут 1–2 секунды или проверка при старте продюсера, а не при каждой смене лидера |

Для асинхронной доставки в Ledger это приемлемая цена: клиент её не видит, платёж уже записан и подтверждён, outbox держит его в PostgreSQL сколько нужно.

## Находки

1. **Самым долгим звеном восстановления была служебная операция, а не Kafka.** Kafka переключила партиции за 8 секунд. Проверка топика при смене лидера outbox зависела от одного конкретного брокера и держала отправку 40 секунд, хотя сама отправка от этого брокера не зависела.
2. **Мёртвая нода не закрывает соединения.** Сессионные блокировки, держатели соединений, сессии — всё, что держится на TCP-соединении, переживает смерть клиента до keepalive. В опытах с PostgreSQL этого не было видно: там вместе с основным экземпляром рвались все соединения.
3. **Замер не должен жить в контейнере того, что замеряют.** Инструменты Kafka — это JVM: запущенные в контейнере брокера, они делят его лимит памяти. Первый прогон инструмента уронил брокер, и отказ одной ноды превратился в отказ двух брокеров.
4. **Одиночные сервисы растекаются по нодам.** Перед прошлыми опытами Traefik и другие одиночные сервисы вручную переносили на `server-0`, но после перезапусков они снова оказались на agent-нодах. Теперь [load/Failover](../load/Failover) сам убирает их с останавливаемой ноды перед прогоном.
5. **`docker stop` — аккуратный отказ.** В прогонах 1–3 лидерство outbox переходило за 1–6 секунд: при остановке контейнера ноды поды получают сигнал и закрывают соединения сами. Keepalive проверен отдельно, обрывом сети: лидерство перешло за 18 секунд (раздел «Обрыв сети»).
6. **Ошибка KRaft на перезапуске лидера кворума.** Брокер, который был лидером кворума, после перезапуска падал, пока лидерство не забрал другой. Сама по себе она не проявилась, только вместе с перезапуском брокера во время отказа другого.
7. **Молчащий партнёр держит клиента на весь его таймаут, а у клиентов Kafka таймауты большие.** Координатор группы — `session.timeout.ms`, 45 секунд по умолчанию; запрос продюсера — `socket.timeout.ms`, 60 секунд. При `docker stop` их не видно: соединения закрываются сразу. При обрыве сети они и задали время простоя; сокращение обоих до 10 секунд убрало из него почти минуту (82 → 31 с у outbox, 4 040 → 45 сообщений у Ledger).

## Что упрощено по сравнению с продакшеном

| На стенде | В продакшене |
|---|---|
| Брокер и контроллер KRaft в одном процессе | Отдельный пул контроллеров: перезапуск брокера не трогает кворум |
| Три узла на одном ноутбуке | Брокеры в разных зонах доступности, `rack` в Strimzi и rack-aware размещение реплик |
| Listener без шифрования и аутентификации | TLS и SCRAM или mTLS, пользователи как `KafkaUser` |
| Тома на диске ноды, удержание 1 час и 64 МБ на партицию | Сетевые или локальные NVMe-диски, удержание по требованиям бизнеса |
| Опыты — остановка ноды и обрыв её сети | Ещё зависший диск, частичная потеря пакетов, перезапуск брокера под нагрузкой |
| После обрыва сети ноду приходится перезапускать: в k3d сеть подов сама не восстанавливается | В настоящем кластере нода, вернувшаяся в сеть, работает дальше |

## Как повторить

```powershell
# Кластер Kafka, топик и распределение лидеров
kubectl -n highload get kafka,kafkanodepool,kafkatopic
kubectl -n highload get pods -l strimzi.io/cluster=kafka -o wide
kubectl -n highload exec kafka-broker-0 -- /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic payments.captured
kubectl -n highload exec kafka-broker-0 -- /opt/kafka/bin/kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status

# Отказ ноды с брокером и лидером outbox: подготовка стенда, замеры, проверки, отчёт в load/reports/failover-<время>/
dotnet run --project load\Failover -c Release -- --node agent-1 --rate 50

# То же, но обрыв сети: нода работает, соединения с ней молчат
dotnet run --project load\Failover -c Release -- --mode partition --node agent-1 --rate 50
```

Проверки инструмента: инварианты Ledger, платежей в базе не меньше успешных ответов, стенд восстановился, outbox перешёл к другой реплике, пока нода лежала, Kafka писала с двумя брокерами, другие брокеры не перезапускались. Если какой-нибудь брокер перезапустится, его последний лог сохраняется рядом с отчётом.
