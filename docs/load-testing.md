# Нагрузочное тестирование этапа 1

Сколько платежей в секунду выдерживает этап 1 на ноутбуке, где у него колено, во что он упирается и сходятся ли деньги под перегрузкой. Путь платежа: k6 → Payments.Api → БД payments (платёж и строка outbox) → OutboxRelay → Kafka → Ledger.Service → БД ledger.

## Коротко

- **Приём платежей держит 1500 в секунду с p99 = 48 мс.** Колено — между 1500 и 2000: на 2000 p99 вырастает в 6 раз, до 290 мс, и k6 уже не успевает отправить 2,3 % платежей. Потолок — около 1850–2100 платежей в секунду, когда процессор ноутбука занят на 94 %.
- **Вся система без отставания журнала держит около 1500 в секунду.** Выше платежи по-прежнему принимаются, а события копятся в outbox и разбираются после пика: outbox работает как буфер.
- **Деньги сходятся и под перегрузкой.** После ступеней до 3000 в секунду, когда в outbox копилось до 116 тысяч событий, сверка показала 1 553 112 проведённых платежей в базе платежей и ровно столько же в журнале. Зависших платежей нет.
- **Асинхронная часть на стенде упирается в проброс порта Docker Desktop.** Весь трафик Kafka идёт через процесс `com.docker.backend`, а Windows держала его в режиме эффективности с приоритетом `Idle`. При загрузке процессора 94 % он почти не получал времени, и relay переносил около 100 событий в секунду вместо 1900.
- **Методика важна не меньше железа.** Одна и та же нагрузка 1500 в секунду в Debug с трейсом каждого запроса и в Release с выборкой трейсов 1 % отличается по времени ответа в 14–26 раз.

## Стенд

| | |
|---|---|
| Ноутбук | тот же, что в [исследовании PostgreSQL](postgres-experiments.md): Intel Core i5-8250U (4 ядра / 8 потоков, под нагрузкой ~2,27 ГГц), 24 ГБ, SSD, Windows 11 |
| PostgreSQL | 15.12, нативно, порт 5433, `shared_buffers` = 1 ГБ |
| Kafka | apache/kafka 4.0.0, один узел в режиме KRaft, в Docker Desktop (WSL2); топик `payments.captured`, 8 партиций |
| Телеметрия | Aspire Dashboard в Docker, OTLP |
| Payments.Api | .NET 10, Release; пул 16 соединений, `statement_timeout` = 5 с; relay читает outbox пачками по 500 |
| Ledger.Service | .NET 10, Release; пул 8 соединений; пачка на партицию — до 500 платежей или 20 мс |
| Банк | заглушка внутри Payments.Api: отвечает без задержки, отклоняет 2 % платежей |
| Генератор нагрузки | k6 на той же машине |

Всё работает на одном ноутбуке и делит один процессор. Это главное ограничение стенда, и ниже оно видно во всех выводах.

## Методика

- **Открытая модель нагрузки.** Сценарий `constant-arrival-rate` в [load/payments.js](../load/payments.js): платежи приходят с заданной частотой, как бы медленно ни отвечал сервис. В закрытой модели, где N пользователей отправляют запросы по кругу, медленный сервис незаметно снижает себе нагрузку.
- **Виртуальные пользователи (VU).** Заранее создаются 10 % от заданной частоты (не меньше 50), всего не больше 500. Если в момент отправки свободного VU нет, k6 платёж не отправляет и считает его в `dropped_iterations`. Таких платежей нет ни в нагрузке, ни в перцентилях, поэтому их доля — отдельный порог.
- **Пороги, при которых ступень засчитывается:** ошибок меньше 1 %, p95 < 200 мс, p99 < 500 мс, не отправлено меньше 1 % запланированных платежей.
- **Сборка и телеметрия.** Сервисы в Release. Трейсы — выборка 1 % (`OTEL_TRACES_SAMPLER=parentbased_traceidratio`, `OTEL_TRACES_SAMPLER_ARG=0.01`); метрики считаются по всем запросам.
- **Прогрев.** Перед первой ступенью — 20 секунд нагрузки не выше 1000 в секунду без замера. Ступени запускает [load/ladder.ps1](../load/ladder.ps1); графики каждой ступени он сохраняет в HTML-отчёт k6.
- **Чистое состояние.** Ступень начинается при пустом outbox.
- **Корректность.** После каждой ступени — `/invariants` (двойная запись, совпадение балансов с проводками, нулевая сумма балансов), после серии — сверка базы платежей с журналом.
- **Отставание журнала.** Сравниваю прирост `payments` в `/invariants` с числом проведённых платежей. Проведённых — 98 % успешных запросов: остальные 2 % отклоняет банк (по сверке 31 492 из 1 584 604).

К этой методике я пришёл не сразу. Первые серии шли в Debug, без прогрева и с трейсом каждого запроса. Что это меняет — в разделе [«Что исказило первые серии»](#что-исказило-первые-серии).

- **1500 — все пороги пройдены.** Отдельный двухминутный прогон на 1500 дал p50 = 3,6 мс, p99 = 76 мс, не отправлено 0,3 %, и журнал к концу прогона полностью догнал платежи.
- **2000 — колено.** p99 вырос в 6 раз, а k6 не отправил 2,3 % платежей.
- **2500 и 3000 — насыщение.** Фактическая скорость перестаёт расти и держится около 1850–2100 в секунду. k6 упёрся в лимит 500 VU (`Insufficient VUs` в логе), поэтому дальше задержка не растёт: при 500 запросах в работе и ~1850 ответах в секунду она около 500 / 1850 ≈ 0,27 с (закон Литтла). Всё, что сверх, уходит в «не отправлено».

После прогонов A–C (ниже), где отставание доходило примерно до 220 тысяч событий, `/invariants` тоже каждый раз возвращал ok.

## Во что упирается приём платежей

![Процессор во время ступени 2500/с](img/load-cpu.png)

- **Процессор ноутбука занят на 94 %:** PostgreSQL — 47,5 %, Payments.Api — 19,9 %, k6 — 16,3 %.
- **База не заставляет себя ждать.** В `pg_stat_activity` из соединений Payments.Api 11–18 простаивают (`idle`, `ClientRead`), активны 1–5. Запросы ждут процессора в самом приложении, а не ответа базы.
- **Прогноз из исследования PostgreSQL подтвердился.** Там без горячих строк база давала ~4600 транзакций в секунду, «то есть грубо ~2 300 платежей при двух транзакциях на платёж». Вышло 1850–2100, и теперь процессор делят ещё k6, сервисы и Kafka.
- **k6 сам отнимает шестую часть процессора.** На отдельной машине для генератора нагрузки потолок был бы выше.

## Асинхронная часть: почему отстаёт журнал

### Наблюдение

На ступенях от 2000 outbox рос почти со скоростью проведения платежей. Оценка — по снимкам `count(*)` раз в несколько секунд:

| Ступень | Рост outbox | Проводится платежей |
|---|---|---|
| 2000 | ~1870 в секунду | ~1910 в секунду |
| 2500 | ~2000 в секунду | ~1810 в секунду |
| 3000 | ~2160 в секунду | ~2040 в секунду |

Значит, под нагрузкой relay почти ничего не переносил. Ledger в это время простаивал: событий не поступало. Как только ступень заканчивалась, outbox быстро разбирался. Ошибок relay в логах Payments.Api нет — он не падал, а голодал.

### Где relay теряет время

Метрика `payments.outbox.stage.duration` делит цикл relay на этапы. P50 при нагрузке 2000 в секунду:

| Этап | Пачка 500 (прогон A) | Пачка 5000 (прогон B) |
|---|---|---|
| Чтение пачки из outbox (`read`) | 5–25 мс | 25–75 мс |
| Отправка в Kafka и ожидание подтверждений (`produce`) | от 2,5 до 10 с и больше | 10 с и больше |
| Удаление отправленных строк (`delete`) | 5–50 мс | до 50 мс, разовый выброс 500 мс |

10 с — верхняя граница корзин гистограммы по умолчанию, на деле могло быть дольше. Когда outbox небольшой (прогон на 1500 в секунду), то же чтение занимает меньше миллисекунды: `EXPLAIN ANALYZE` показал 0,9 мс. Postgres для relay не узкое место — узкое место отправка в Kafka.

### Эксперименты A, B, C

Нагрузка 2000 в секунду, 2 минуты, прогрев, пустой outbox на старте.

| | A | B | C |
|---|---|---|---|
| Пачка relay | 500 | 5000 | 5000 |
| Приоритет `com.docker.backend` | `Idle` (режим эффективности) | `Idle` | `Normal` |
| Проведено за прогон, с прогревом | 246 тыс. | 251 тыс. | 243 тыс. |
| Дошло до журнала за прогон | 32 тыс. (13 %) | 29 тыс. (12 %) | 71 тыс. (29 %) |
| Приём: p50 / p95 / p99, мс | 13 / 260 / 425 | 9 / 126 / 266 | 36 / 290 / 412 |
| Не отправлено | 3,5 % | 1,4 % | 4,8 % |

![Relay под нагрузкой](img/load-relay.png)

- **B: большие пачки не помогли.** Если бы relay ограничивало время одного обмена с Kafka, пачка в 10 раз больше дала бы в 10 раз больше событий. Вместо этого время отправки выросло вместе с пачкой: путь до Kafka ограничен объёмом данных, а не числом обменов.
- **Почему путь до Kafka такой узкий.** Kafka работает в виртуальной машине Docker Desktop, а порт 9092 на Windows слушает процесс `com.docker.backend` и копирует байты внутрь неё. Windows держала этот процесс в режиме эффективности, то есть с приоритетом `Idle` и правом выполнять его на медленных ядрах. При загрузке процессора 94 % он получал время только в паузах. Виртуальная машина с Kafka в это время занимала 0,6 % процессора: до брокера почти ничего не доходило.
- **C: обычный приоритет помог больше чем вдвое.** До журнала дошла 71 тысяча событий против 29–32, но и это меньше трети проведённых платежей. По оценке из `pg_stat_user_tables` relay под нагрузкой переносил около 1000 событий в секунду, а до журнала к концу прогона дошло меньше: Ledger читает Kafka через тот же процесс Docker.
- **Процессор приходится делить.** Время, которое получила асинхронная часть, ушло у приёма платежей: в C время ответа хуже, чем в B. Разброс между прогонами большой — A и B отличаются вдвое при одном изменённом параметре, — но направление логичное.

**Итог.** На 2000 в секунду этому ноутбуку не хватает процессора на обе половины системы: приём держится, только пока асинхронная часть голодает. Без отставания журнала стенд держит около 1500 в секунду. Выше outbox работает как буфер и разбирается после пика, без потерь.

## Особенности стенда

- **Генератор нагрузки на той же машине** забирает 16 % процессора.
- **Проброс порта Docker Desktop и режим эффективности Windows.** Перед прогоном проверяй приоритет процесса, который слушает порт Kafka, — должен быть `Normal`. После перезапуска Docker Desktop режим эффективности может вернуться.
- **Лимит 500 VU** ограничивает сверху измеренную задержку на насыщении.
- **Отказы TCP в первую секунду**, когда заранее создано 250–300 VU и больше.
- **`/invariants` читает все проводки.** При 3,5–4,5 миллиона проводок проверка под нагрузкой не укладывалась в `statement_timeout` = 10 с и возвращала 500. Теперь у неё свой лимит — 2 минуты (`SET LOCAL statement_timeout`), а консьюмер сохраняет свои 10 секунд.
- **Retention Kafka на стенде — 1 час и 64 МБ на партицию.** Если Ledger отстанет сильнее, события удалятся непрочитанными. В продакшене retention должен быть с запасом больше худшего отставания.
- **Оценка размера outbox.** `n_live_tup` из статистики — приблизительная. `count(*)` точнее, но под нагрузкой по раздутой таблице сам выполнялся секундами.

## Что из этого следует для продакшена

- **Kafka — на своих машинах**, без посредника между сервисом и брокером. Relay и консьюмеры масштабируются отдельно от приёма платежей.
- **Метрики отставания асинхронной части и алерт на них:** возраст самой старой строки outbox и lag консьюмера Ledger. В этих прогонах они сразу показали бы проблему, а не по сверке.
- **Рабочая нагрузка — с запасом ниже точки, где система держится целиком.** Для этого стенда это около 1100–1200 платежей в секунду.
- **Outbox как буфер — достоинство архитектуры:** приём платежей не зависит от Kafka. Но буфер нужно мониторить, а retention брокера — считать от худшего отставания.
- **Замерять в Release и с выборкой трейсов, генератор нагрузки — на отдельной машине.**

## Дальнейшие шаги

- Метрики отставания: возраст самой старой строки outbox (gauge в Payments.Api) и lag консьюмера Ledger.
- Точное колено: ступени от 1500 до 2000 через 100.
- Длительный прогон: 10–15 минут на ~1200 в секунду — чекпоинты, автовакуум, стабильность.
- Снизить нагрузку на процессор от Postgres: автоподготовка запросов в Npgsql (`Max Auto Prepare`), микропачки в Payments.Api.
- Статистика клиента Kafka (librdkafka: `rtt`, `int_latency`): разделить задержку внутри клиента и на пути до брокера.
- Хаос-тест (этап 3): остановить Ledger и Payments.Api посреди нагрузки и проверить сверку.

## Как воспроизвести

Сервисы — каждый в своём окне:

```powershell
docker compose up -d

# окно Ledger
$env:OTEL_TRACES_SAMPLER = "parentbased_traceidratio"
$env:OTEL_TRACES_SAMPLER_ARG = "0.01"
dotnet run -c Release --project src\Ledger.Service

# окно Payments.Api: те же две переменные и метрики раз в 5 секунд
$env:OTEL_TRACES_SAMPLER = "parentbased_traceidratio"
$env:OTEL_TRACES_SAMPLER_ARG = "0.01"
$env:OTEL_METRIC_EXPORT_INTERVAL = "5000"
dotnet run -c Release --project src\Payments.Api
```

Приоритет процесса, который пробрасывает порт Kafka, — должен быть `Normal`:

```powershell
Get-Process -Id (Get-NetTCPConnection -LocalPort 9092 -State Listen).OwningProcess | Select-Object Id, ProcessName, PriorityClass
```

Во время прогона — что делают соединения Postgres и сколько строк в outbox (`psql -p 5433 -U postgres -d payments`):

```sql
SELECT datname, state, wait_event_type, wait_event, count(*),
       (SELECT n_live_tup FROM pg_stat_user_tables WHERE relname = 'outbox') AS outbox
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND pid <> pg_backend_pid()
GROUP BY 1, 2, 3, 4
ORDER BY 5 DESC \watch 2
```

Ступени и эксперимент с пачкой relay:

```powershell
powershell -ExecutionPolicy Bypass -File load\ladder.ps1 -Rates "1500,2000,2500,3000"
powershell -ExecutionPolicy Bypass -File load\ladder.ps1 -Rates "2000" -Duration 120s

# пачка relay 5000: в окне Payments.Api перед dotnet run
$env:Outbox__BatchSize = "5000"
```

Этапы цикла relay — в дашборде: Metrics → `payments-api` → `payments.outbox.stage.duration`, фильтр `stage`.

Сверка, когда outbox опустеет: `captured` должно совпасть с `payments` из `/invariants`, `stuck` и `outbox` — нули.

```powershell
psql -p 5433 -U postgres -d payments -c "SELECT count(*) FILTER (WHERE status = 'captured') AS captured, count(*) FILTER (WHERE status = 'declined') AS declined, count(*) FILTER (WHERE status = 'created') AS stuck, (SELECT count(*) FROM outbox) AS outbox FROM payments"
Invoke-RestMethod http://localhost:5200/invariants
```

Очистка перед новой серией — после сверки, при остановленных сервисах:

```powershell
psql -p 5433 -U postgres -d payments -c "TRUNCATE payments, outbox"
psql -p 5433 -U postgres -d ledger -c "TRUNCATE postings, processed_payments, accounts"
```

# Этап 3: горячий продавец

Один продавец получает половину или 90 % всех платежей. Вопрос: мешает ли он остальным 49 — при приёме платежей и в асинхронной части, где все его события попадают в одну партицию Kafka. Ниже замер **до** изменений лимитера и **после** шага 4а, где лимитер перестал выключаться при сбоях Redis.

## Коротко

- **Лимитер защищает остальных продавцов, пока отвечает Redis.** На 1500 платежей в секунду с горячим продавцом на 90 % у остальных p99 = 126 мс и пороги пройдены. Без лимитера — 758 мс, и k6 не отправил 15 % платежей.
- **Когда Redis не отвечает, лимитер выключается — и горячий продавец перегружает стенд.** Лимитер ждёт Redis 100 мс и после таймаута пропускает всех без лимита 5 секунд. В повторе 5c таких таймаутов было 211: горячий продавец получил 512 платежей в секунду при лимите 200, p99 остальных вырос до 1053 мс, не отправлено 18 %. В прогоне 2 (горячий на 50 %) медиана — 2962 платежа сверх лимита за 2 минуты.
- **Kafka изолирует горячего продавца в асинхронной части.** Без лимитера его партиция получает 1000–1200 событий в секунду, её lag доходит до 9 500 (медиана максимумов; в 6a — 18 000), у остальных партиций — около 170. Журнал догоняет за 1–5 секунд после конца нагрузки.
- **Колено стенда без перекоса — между 1000 и 1500 в секунду.** На этапе 1 оно было между 1500 и 2000, но тогда банк был заглушкой внутри Payments.Api. Теперь это эмулятор по HTTP с задержкой 50 ± 20 мс, и на каждый платёж есть запрос к Redis.
- **Деньги сходятся:** `/invariants` ok после каждого из 18 повторов.
- **После шага 4а сбой Redis больше не снимает лимит.** На время сбоя каждый экземпляр Payments.Api ограничивает продавцов сам. В остальное время платёж проходит, только если согласны и Redis, и локальный бакет. Сверх лимита — 0 во всех 15 повторах с лимитером. До шага 4а худший повтор дал 37 036.
- **Таймауты Redis на 1500 в секунду — от загрузки ноутбука, а не от Redis.** Redis отвечает всегда, просто иногда позже 100 мс: медиана таких ответов — 121 мс. Ответ ждёт процессора вместе со всем стендом.
- **Раз в 5 минут стенд тормозил из-за пула соединений Npgsql.** Пул закрывал простаивающие соединения, а нагрузка тут же открывала их снова. С `Minimum Pool Size`, равным максимуму, это прошло.
- **С двумя экземплярами Payments.Api сбой Redis на 10 секунд стоит около 3 000 платежей сверх лимита**, с одним — от 0 до 83. Локальный бакет каждого экземпляра видит только половину платежей продавца и к началу сбоя полон.
- **Квота горячего продавца (шаг 5) работает как условие договора.** С квотой 1000 в секунду он получает 429 только сверх неё, у остальных нет ни одного 429, а их p99 — как при равномерной нагрузке того же объёма: 185 мс против 167.
- **Отказ банка одному продавцу больше не останавливает остальных (шаг 6).** Пока все вызовы банка шли через один circuit breaker, отказы горячего продавца размыкали его для всех: у остальных 99,9 % ответов — 202. Со своим конвейером у продавца с квотой — 0 %.

## После: локальный лимит при сбое Redis

Шаг 4а изменил две вещи в `Payments.Api/RateLimiting`:

- **Пока Redis не отвечает, лимит считает сам экземпляр.** Раньше после таймаута лимит не действовал 5 секунд. Теперь в это время решает `LocalMerchantLimiter` — токен-бакет на продавца в памяти процесса (`PartitionedRateLimiter`) с тем же лимитом, 200 в секунду и всплеск 400.
- **Breaker замыкает только пробный запрос.** Раньше его замыкал любой ответ Redis, в том числе на запрос, отправленный до сбоя. Под нагрузкой breaker мерцал: размыкался и замыкался по нескольку раз в секунду, и каждый раз запросы снова ждали зависший Redis. Теперь после паузы в 5 секунд в Redis идёт один пробный запрос, и только его ответ возвращает общий лимит.

- **Худший случай закрыт.** Из девяти повторов с горячим продавцом и лимитером больше всего сверх лимита — 1 858 (2a, три сбоя Redis). До шага 4а был повтор 5c: 37 036 сверх лимита, горячий продавец получал 512 платежей в секунду при лимите 200, а остальные — p99 = 1053 мс.

Первые 400: локальный бакет в начале сбоя полный, он не знает, сколько продавец уже потратил в Redis. Ещё до 400: бакет в Redis за время сбоя пополняется, потому что не видит платежей, пропущенных локально. Оба компромисса записаны в `LocalMerchantLimiter`.
- **Типичный повтор прогона 5 стал хуже: 38 → 754.** До шага 4а большинство «отключений» были мерцанием: breaker замыкался через миллисекунды, и короткий сбой почти ничего не пропускал. Теперь каждый сбой — это 5 секунд локального лимита и два всплеска. Это плата за то, что длинный сбой больше не снимает лимит совсем.
- **Мерцания больше нет.** В логе строки идут парами: «did not answer», затем «answers again», когда ответил пробный запрос, — обычно через 5 секунд, изредка через 10, если первый пробный тоже не дождался Redis. На 1500 в секунду без перекоса (прогон 4) Redis не отвечал за 100 мс 16 раз за повтор. Продавцам это ничем не грозило: у каждого около 30 платежей в секунду, ниже лимита.
- **Время ответа между матрицами сравнивать нельзя.** Прогон 6 идёт без лимитера, шаг 4а его не касается, а p99 остальных упал с 758 до 383 мс, «не отправлено» — с 15 % до 0,81 %. ### Redis и локальный бакет решают вместе

Последняя часть шага 4а:

- **Платёж проходит, только если согласны оба бакета** — не только во время сбоя, но и после. Redis разрешил — фильтр берёт токен и из локального бакета; токена нет — 429. Но часть разницы может дать и короткая пауза: с паузой 5 секунд прогон 4 около 60 секунд из 120 обходился без Redis, теперь — около 37.

### Откуда таймауты Redis на 1500 в секунду

По новым строкам лога, матрица 19:00–19:40. Сбоев 132: 111 — в прогоне 4, 7 — на прогреве, 14 — в остальных прогонах.

- **Redis отвечает всегда, просто поздно.** Все 132 вызова, которые лимитер перестал ждать, получили ответ, ни один не упал по таймауту самого StackExchange.Redis. Для 114 известно, через сколько: медиана — 121 мс, 9 из 10 — до 178 мс, самый долгий — 462 мс.
- **GC ни при чём.** За 100 мс ожидания GC останавливал процесс в 19 сбоях из 132, на 17–82 мс, и ни разу на все 100.
- **Дело в нагрузке стенда, а не Redis.** Почти все сбои — в прогоне 4, где принимаются все 1500 платежей в секунду. В прогоне 5 запросов к Redis столько же, но три четверти из них кончаются быстрым 429, и сбой один на повтор. В момент сбоя в пуле Payments.Api 10–11 потоков, а в очереди ждёт работа: медиана — 32 задачи, до 287. Работа идёт, но процессора не хватает: ноутбук на 4 ядрах держит весь стенд, и ответ Redis ждёт своей очереди, как и всё остальное. Самые долгие задержки задевают и звонки в банк: в те же секунды бывают пачки таймаутов по 300 мс, до 185 за секунду, а эмулятор банка работает не в Docker.
- **Лимиту эти сбои больше не вредят.** Секунда локального лимита у одного экземпляра — тот же лимит. Поэтому таймаут 100 мс увеличивать не нужно: он ограничивает, сколько платёж ждёт Redis, который действительно завис.
- **Отдельно — сбой раз в 5 минут.** Сбои вне прогона 4 почти все приходятся на 5, 10, 15… минут после старта Payments.Api — с точностью до нескольких секунд, в обеих матрицах. Это пул соединений Npgsql, ниже.

### Сбой раз в 5 минут: пул соединений Npgsql

- **Тормозил весь стенд, а не Redis.** В матрицах 17:51 и 19:00 в секунды +5, +10, +15… минут от старта Payments.Api собственные запросы матрицы к Postgres отвечали 15–55 мс вместо 1–3, к Kafka — 48–183 мс вместо 10–15, а в outbox на секунду копилось до 220 строк вместо обычных 10–50.
- **Причина — чистка пула в Npgsql.** Раз в `Connection Idle Lifetime`, по умолчанию 300 секунд, Npgsql закрывает столько соединений, сколько простаивало в медиане его замеров; замеры он делает раз в 10 секунд. Под нагрузкой эти соединения нужны снова, и пул открывает их все разом. В песочнице ровно через 5 минут после открытия пула 11 из 16 соединений Payments.Api и соединение Ledger открылись заново за 0,4 секунды. На Windows каждое соединение с Postgres — новый процесс сервера.
- **Исправление — `Minimum Pool Size`, равный `Maximum Pool Size`**: 16 у Payments.Api, 8 у Ledger. Ниже минимума Npgsql соединения не закрывает. В песочнице через 5 минут 40 секунд все соединения остались теми, что открылись при старте.
- **На ноутбуке всплески пропали.** В двух сериях с паузой Redis (ниже) в отметки +5 и +10 минут Postgres отвечал матрице за 1–9 мс, Kafka — за 7–33 мс, и сбоев Redis в эти секунды не было.

### Два экземпляра Payments.Api

Два новых параметра матрицы. `--instances 2` запускает второй экземпляр на порту 5101, и k6 шлёт запросы обоим по очереди; outbox и поиск зависших платежей ведёт один из них, тот, что взял лидерскую блокировку. `--redis-pause 10` в середине каждого повтора на 10 секунд задерживает все команды к Redis (`CLIENT PAUSE`) — как зависший Redis, одинаково в каждом повторе. Две серии 09.11, прогоны 2 и 5 по три повтора, обе с `--fresh`: 20:21–20:34 с одним экземпляром, 20:36–20:50 с двумя. Медианы:

| Прогон | Платежей/с | Горячий | Экземпляров | p99 остальных, мс | p99 горячего (201), мс | Горячему прошло, /с | Сверх лимита | Сбоев Redis | Lag горячей партиции |
|---|---|---|---|---|---|---|---|---|---|
| 2 | 1000 | 50 % | 1 | 123 | 135 | 203 | 0 | 1 | 151 |
| 2 | 1000 | 50 % | 2 | 141 | 163 | 229 | 3 050 | 2 | 301 |
| 5 | 1500 | 90 % | 1 | 112 | 143 | 204 | 51 | 1 | 53 |
| 5 | 1500 | 90 % | 2 | 122 | 320 | 227 | 2 879 | 2 | 654 |

**Сбоев Redis** с двумя экземплярами — по строке от каждого: одна пауза дала две строки.

- **С одним экземпляром пауза почти ничего не стоит:** сверх лимита от 0 до 83 за повтор, меньше полсекунды лимита. Локальный бакет к началу сбоя пуст, как и бакет Redis, а после сбоя не даёт Redis пропустить наполнившийся за паузу всплеск.
- **С двумя — около 3 000 за одну паузу.** Каждый экземпляр видит половину платежей, которые пропустил Redis, — 100 в секунду при пополнении 200, — так что к началу сбоя его локальный бакет полон. Пауза вместе с ожиданием пробного запроса длится около 10,2 секунды, и за это время каждый экземпляр пропускает свои 400 и по 200 в секунду: вместе около 4 900, а по лимиту — около 2 000. После паузы оба бакета пусты, но пополняются вдвое быстрее, чем Redis, и пропускают ещё около 200 из его всплеска. Итого около 3 000; медианы — 3 050 и 2 879.
- **Повторы выше медианы — с лишним сбоем.** В 2b (3 592) и 5b (3 477) Redis ещё раз не ответил вне паузы. Пока бакеты полны, секунда локального лимита добавляет ещё сотни платежей: всплеск и секунду лимита на каждый экземпляр, который не дождался Redis.
- **Платят горячий продавец и его партиция, не остальные.** p99 остальных — 141 и 122 мс против 123 и 112 с одним экземпляром, пороги пройдены во всех повторах. Платежей горячего продавца за паузу проходит больше: его p99 в прогоне 5 — 320 мс против 143, lag его партиции — 654 против 53.
- **Это тот компромисс, что записан в `LocalMerchantLimiter`.** Бакет, который следует за Redis, помогает, только если экземпляр видит все платежи продавца. При N ≥ 2 экземплярах сбой длиной T стоит около N × всплеск + (N − 1) × лимит × T.

**Что ещё можно сделать:**
- Давать локальному бакету долю лимита: 1/N лимита и всплеска на каждый из N экземпляров. Тогда во время сбоя они вместе пропускают один лимит, а пока Redis отвечает, каждый видит свою долю платежей и снова следует за Redis. Для этого нужно знать N — например, каждый экземпляр раз в несколько секунд отмечается в Redis ключом с коротким TTL, а во время сбоя действует последнее известное число. Цена — неровная балансировка: если продавцу шлёт запросы в основном один экземпляр, его доля станет узким местом и, пока Redis отвечает, будет отказывать в платежах, которые Redis пропускает.

## Шаг 5: квоты продавцов

У крупного продавца своя квота поверх общего лимита: `RateLimiting:Merchant:Overrides` в `appsettings.json`, merchantId → скорость и всплеск. Квоты перечитываются при изменении файла, без перезапуска, а отказы размечены атрибутом `quota` — `default` или `override`. Горячему продавцу дана квота 1000 в секунду и всплеск 2000 (`--hot-quota 1000`): стенд держит около 1500 в секунду, и 500 остаётся остальным.

Матрица 09.11, 23:22–23:48, с `--fresh`, прогоны 1, 3, 4 и 5 по три повтора. Медианы:

| Прогон | Платежей/с | Горячий | Стенд принимает, /с | p99 остальных, мс | 429 у горячего | Горячему прошло, /с | Lag: горячая / прочие партиции |
|---|---|---|---|---|---|---|---|
| 1 | 1000 | — | ≈ 1 000 | 167 | — | — | — / 125 |
| 3 | 1000 | 90 % | ≈ 1 000 | 185 | 0 % | 900 | 543 / 11 |
| 4 | 1500 | — | ≈ 1 500 | 265 | — | — | — / 230 |
| 5 | 1500 | 90 % | ≈ 1 165 | 199 | 25 % | 1 015 | 472 / 14 |

- **429 у горячего продавца — только сверх квоты.** В прогоне 3 он шлёт 900 в секунду, меньше квоты, и отказов у него нет. В прогоне 5 шлёт 1 350, а проходит 1 015: 1000 в секунду и всплеск 2000, растянутый на 120 секунд. Сверх квоты — 0 во всех повторах, у остальных 49 продавцов — ни одного 429.
- **Соседи замечают горячего продавца не больше, чем равномерную нагрузку того же объёма.** Прогон 3 принимает столько же, сколько прогон 1, и p99 остальных — 185 мс против 167. Прогон 5 принимает около 1 165 в секунду, и его 199 мс лежат между 167 при 1000 и 265 при 1500 без перекоса. Разница меньше разброса повторов: в 1c, без горячего продавца, p99 был 855 мс.
- **Цена квоты — нагрузка, которую раньше отсекал лимит.** С общим лимитом 200 стенд в прогонах 3 и 5 принимал 300–350 платежей в секунду, и p99 остальных был 84–126 мс. С квотой горячий продавец проходит, и стенд работает у своего колена, как без перекоса.
- **Горячая партиция отстаёт сильнее остальных.** При 900–1000 событиях в секунду её lag доходит до 472–543 сообщений (медианы максимумов), у прочих — 11–14, и журнал догоняет за секунду после нагрузки. С этих цифр начинается эксперимент шага 7.
- **Серия — после перезагрузки ноутбука.** Предыдущая серия того же вечера шла на стенде, замедлившемся к концу дня в 3–10 раз даже в прогонах без горячего продавца: таймаутов звонков в банк было 7 660 против 979 здесь. В сравнение она не взята.

## Шаг 6: банк отказывает одному продавцу

Эмулятор отвечает 500 на каждую авторизацию горячего продавца, а остальных обслуживает как обычно (`--bank-fails-hot`, в эмуляторе — `BANK_ERROR_MERCHANT`). Нагрузка — прогон 3: 1000 платежей в секунду, 90 % у горячего продавца. Квота 1000 в секунду (`--hot-quota 1000`) нужна, чтобы все его платежи доходили до банка. По одному повтору с `--fresh`, 10.11: «до» — 00:33–00:36 на коммите `0c0c6fa`, «после» — 00:37–00:40 на `11ddf30`.

До шага 6 все вызовы банка шли через один конвейер устойчивости с одним circuit breaker. После у продавца со своей квотой свой конвейер (`BankPipeline`), у остальных — общий.

| | 202 у остальных | 202 у горячего | p99 остальных, мс | Какой breaker размыкался | Восстановление |
|---|---|---|---|---|---|
| До: один конвейер | 99,9 % (11 972 из 11 987) | 100 % | 10 | общий, 36 раз | стоит: 15 пауз «Bank unavailable», ни одного разобранного платежа |
| После: свой у горячего | 0 % (из 12 139) | 100 % | 117 | только `merchant-1`, 36 раз | отклонило 92 000 платежей горячего продавца |

Размыкания breaker — по логу Payments.Api за прогрев и прогон, около трёх минут: раз в 5 секунд, после каждой паузы.

- **До: отказ банка одному продавцу останавливает всех.** 90 % вызовов — отказы горячего продавца, и общий breaker (размыкается при 50 % отказов) после каждой паузы почти сразу размыкается снова. Остальные 49 продавцов получают 202 почти на каждый платёж, хотя банк их обслуживает. Их p99 = 10 мс — это быстрый отказ без вызова банка, а не хорошая работа.
- **И восстановление тоже стоит.** Поиск решения шёл через тот же breaker, а проход восстановления прерывается на первом платеже без ответа. Когда банк снова ответит, платежи остальных продавцов будут отклонены: банк их не видел. Для клиента это 202, а потом отказ.
- **После: размыкается только breaker горячего продавца.** Общий не разомкнулся ни разу, у остальных ни одного 202, пороги пройдены. Горячий продавец получает 202 сразу, без трёх попыток: его breaker открыт.
- **Восстановление работает без пауз.** Поиск решения идёт через общий конвейер, банк отвечает на него 404 — решения нет, — и платежи горячего продавца отклоняются: 92 000 к концу прогона.
- **p99 остальных — 117 мс, меньше 185 в прогоне 3 шага 5.** Платежи горячего продавца до банка не доходят и не проводятся: ни outbox, ни Kafka, ни журнала, только запись в `created` и ответ 202. Стенд проводит около 100 платежей в секунду, а не 1000, зато параллельно восстановление отклоняет сотни в секунду.

## Как воспроизвести

Нужны Postgres и `docker compose up -d`; эмулятор банка и сервисы матрица запускает сама:

```powershell
dotnet run --project load\Matrix -c Release -- --fresh --repeats 3

# Пауза Redis на 10 секунд в каждом повторе: один экземпляр Payments.Api, потом два
dotnet run --project load\Matrix -c Release -- --fresh --runs 2,5 --repeats 3 --redis-pause 10
dotnet run --project load\Matrix -c Release -- --fresh --runs 2,5 --repeats 3 --redis-pause 10 --instances 2

# Квота 1000 в секунду для горячего продавца и прогоны без перекоса для сравнения
dotnet run --project load\Matrix -c Release -- --fresh --runs 1,3,4,5 --repeats 3 --hot-quota 1000

# Банк отказывает горячему продавцу: «до» — на коммите 0c0c6fa, «после» — на 11ddf30
dotnet run --project load\Matrix -c Release -- --fresh --runs 3 --repeats 1 --hot-quota 1000 --bank-fails-hot
```

Итог — `load\reports\matrix-<время>\table.md`, рядом итоги и графики k6, замеры outbox и lag по секундам, логи сервисов. Полная матрица — около 50 минут, серия с паузой Redis — около 18, прогон шага 6 — около 5.
