# Объём первой версии React-фронтенда

## Назначение

Учебный интерфейс для демонстрации и ручной проверки платёжной платформы. Пользователь — разработчик или тестировщик закрытого стенда. Фронтенд вызывает HTTP API и не обращается напрямую к PostgreSQL, Kafka или Redis.

Это не интерфейс для реального покупателя или продавца: в текущем API нет аутентификации и авторизации пользователей.

## Что входит в первую версию

### 1. Создать платёж и посмотреть результат

- Форма принимает ID продавца и сумму в рублях. Валюта фиксирована: RUB.
- Данные банковской карты не запрашиваются: текущий API их не принимает.
- Перед отправкой сумма переводится в копейки; API принимает положительную сумму до 1 млрд рублей.
- Фронтенд отправляет `POST /payments` с новым уникальным `Idempotency-Key` и полями `merchantId`, `amount` (в копейках), `currency`.
- После ответа показывает ID платежа, продавца, сумму, валюту, комиссию, время создания и статус.
- При `202 Accepted` показывает «Обрабатывается» и опрашивает `GET /payments/{id}` до конечного статуса. Опрос прекращается при `captured`, `declined` или `voided`; для `created` и `authorized` платёж считается незавершённым.
- Повторная отправка после сетевой ошибки использует тот же ключ идемпотентности, пока исход предыдущего запроса не выяснен. Новое намеренное создание платежа получает новый ключ.

### 2. Найти платёж по ID

- Поле для UUID платежа и действие «Найти».
- Запрос `GET /payments/{id}`.
- Показ тех же сведений и статуса, что и после создания.
- Отдельные состояния интерфейса: загрузка, платёж не найден (404), неверный ID и ошибка сети.

### 3. Посмотреть баланс продавца

- Поле ID продавца и действие «Показать баланс».
- Запрос `GET /balances/merchants/{merchantId}`.
- Показ ID продавца и баланса в рублях с корректным переводом из копеек.
- Если Ledger ещё не создал счёт, показать пустой баланс как отдельное понятное состояние (API может вернуть 404).

## Общие требования

- Показывать ошибки API понятным текстом; для ответа `429` учитывать `Retry-After`.
- Не создавать повторный платёж автоматически после неоднозначной сетевой ошибки.
- Суммы отображать в рублях с двумя знаками после запятой; внутренние значения хранить и передавать в копейках.
- Адреса Payments API и Ledger задавать конфигурацией окружения, не вшивать в компоненты.
- На локальной разработке разрешить в CORS только адрес dev-сервера фронтенда. В Kubernetes отдавать интерфейс через общий входной адрес и маршрутизировать API-запросы к соответствующим сервисам.
- Интерфейс предназначен только для закрытого учебного стенда, пока у API нет проверки личности и прав пользователя.

## Не входит в первую версию

- История или список платежей: Payments API пока не предоставляет endpoint списка. Не загружать историю обходом ID.
- Регистрация, вход, роли пользователей и управление продавцами.
- Ввод данных карты, возвраты и ручное управление статусами.
- Административные дашборды с метриками Prometheus/Grafana; это отдельный интерфейс от телеметрии стенда.

## Критерии готовности объёма

Этот документ фиксирует поведение трёх сценариев первой версии. Их интерфейс и HTTP-вызовы реализованы в `frontend/src/App.tsx` и `frontend/src/api.ts`; локальный CORS настроен для адресов Vite dev-сервера в `appsettings.Development.json` обоих API. Kubernetes использует общий входной адрес для UI и API, чтобы браузерные запросы шли на тот же origin.
