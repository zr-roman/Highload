# GitOps: стенд в k3d под Argo CD

Что работает в кластере — то, что лежит в `deploy/k8s` на ветке `main` в GitHub. Изменения доходят до кластера через `git push`, а не через `kubectl apply`; откат — `git revert`. Кластер, манифесты и замеры — в [deploy/k8s/README.md](../deploy/k8s/README.md) и [load-testing.md](load-testing.md#стенд-в-kubernetes-k3d).

## Как устроено

```
 git push ──► GitHub: deploy/k8s на main
                  │  Argo CD читает раз в 3 минуты, сразу — по Refresh
                  ▼
             Argo CD (namespace argocd)
                  │  kustomize build deploy/k8s, server-side apply
                  ▼
             namespace highload: сервисы, Kafka, Redis, Traefik-маршруты, PDB, HPA
```

- **Приложение** — [deploy/argocd/highload.yaml](../deploy/argocd/highload.yaml). Применяется руками один раз и лежит вне `deploy/k8s`: иначе приложение управляло бы само собой, и удаление его из git удалило бы его из кластера.
- **`automated` с `prune` и `selfHeal`.** Удалённое из git удаляется из кластера; правка руками (`kubectl scale`, `edit`) откатывается к тому, что в git.
- **Kustomize, без Helm.** `deploy/k8s` уже был kustomization: Argo CD собирает его сам.
- **Argo CD без dex** (`argocd-dex-server` — 0 реплик): SSO на стенде не нужен, а память на ноутбуке на счету.

## Решения и почему

| Что | Почему |
|---|---|
| Пароль Grafana — SealedSecret в git, а не Secret, созданный руками | В кластере нет ничего, чего нет в git: стенд поднимается из репозитория, а смена пароля — коммит с историей. Расшифровать может только контроллер в кластере. Цена — закрытый ключ контроллера живёт вне git, и без его копии новый кластер старые файлы не откроет |
| Пароль PostgreSQL генерирует оператор CloudNativePG в кластере | Его нет в git вообще, даже зашифрованного: сервисы читают Secret `pg-app` ([postgres-failover.md](postgres-failover.md)). Цена — пароль знает только этот кластер; новый кластер получит новый |
| `ServerSideApply=true` | Поля, которые API-сервер дописывает по умолчанию (`volumeClaimTemplates` у StatefulSet Kafka), не считаются разницей. Без этого приложение вечно `OutOfSync` — то же `statefulset.apps/kafka configured` на каждом `kubectl apply`, что было весь этап 2 |
| `replicas` нет в Deployment Payments.Api, `ignoreDifferences` для `/spec/replicas` | Числом реплик управляет HPA. Число в манифесте Argo CD возвращал бы при каждой синхронизации, споря с HPA |
| Тег образа = короткий хеш коммита, в блоке `images:` в `kustomization.yaml` | С тегом `:dev` новый образ для Kubernetes и Argo CD неотличим от старого, и новая версия не выкатывается. Новый тег в git — это и есть новая версия |

## Выкатка новой версии

Backend CI проверяет backend-код, собирает образы изменившихся backend-сервисов и записывает теги в git. [Frontend CI](../.github/workflows/frontend-ci.yml) отдельно собирает React, проверяет Docker-образ, сканирует и подписывает его, публикует в GHCR и коммитит тег фронтенда в `deploy/k8s/kustomization.yaml`. Argo CD видит новый тег и обновляет кластер. Git остаётся единственным входом в кластер: CI сам с ним не соединяется.

```
 git push ──► GitHub Actions
                 │  тесты: .NET (Testcontainers), Go (go test -race), Python (ruff, pytest)
                 │  что выпускать: deploy/ci-release.py plan frontend
                 ▼
            образы изменившихся сервисов ──► ghcr.io/zr-roman/<сервис>:<коммит>
                 │
                 ▼
            коммит бота «Release: … (CI)»: newTag и newName в kustomization.yaml
                 │
                 ▼
            Argo CD ──► rolling update
```

Для фронтенда этот же путь проходит через Frontend CI: после React-сборки и сборки контейнера он публикует `ghcr.io/zr-roman/frontend:<коммит>` и отдельным коммитом обновляет тег `frontend` в Kustomize. Маршрут `/` обслуживает React, а более длинные `/payments`, `/balances` и `/invariants` остаются за API.

- **Выпускается то, что изменилось с прошлого образа, а не с прошлого push.** Тег — коммит, из которого собран образ, поэтому [deploy/ci-release.py](../deploy/ci-release.py) спрашивает git: менялись ли исходники сервиса (свой каталог плюс общие `src/Platform`, `src/Contracts`, `Directory.*.props`) между тегом и HEAD. Ни списка «что было в последнем push», ни состояния между прогонами: отменённый прогон ничего не теряет, следующий выпустит всё, что отстало. Тег `dev` — не коммит: такой сервис выпускается.
- **Новый push отменяет старый прогон** (`concurrency` с `cancel-in-progress`) — по той же причине это безопасно.
- **Push бота не запускает CI** — так GitHub обходится с `GITHUB_TOKEN`, иначе релиз запускал бы релиз. Документация не запускает сборочные проверки; изменения манифестов проверяет отдельный workflow.
- **Тяжёлые проверки запускаются по своим каталогам.** На `push` Backend CI реагирует на backend-код, `tests/**` и общие файлы сборки; Frontend CI — на `frontend/**` и `.dockerignore`. На каждый PR запускаются лёгкие jobs определения изменений и итоговые checks `Backend checks` и `Frontend checks`. Их можно выбрать как обязательные в правилах ветки `main`; условные jobs тестирования и сборки для этого не подходят, потому что могут пропускаться. Backend-тесты и React-сборка с контейнером выполняются только при изменениях соответствующей части, а пропуск условной job считается успешным для итогового check. Поэтому PR только с фронтендом не запускает backend-тесты и не пересобирает backend-образы. Изменение обеих частей запускает обе проверки. Изменения `deploy/**` отдельно проверяет `manifests.yml`.
- **Образы публичные**, как и репозиторий: k3d скачивает их без пароля. Пакеты ghcr.io унаследовали видимость репозитория.
- **Тесты — до образов.** Задача сборки ждёт все три набора тестов: красный тест не доходит до кластера.

Без CI или без интернета — [deploy/release.ps1](../deploy/release.ps1): собирает образ на ноутбуке под тем же именем `ghcr.io/zr-roman/…`, загружает его в ноды (`k3d image import`, `imagePullPolicy: IfNotPresent` — кластер не пойдёт за ним в реестр) и коммитит тег:

1. Отказывается работать, если исходники сервиса не закоммичены: тег назвал бы коммит, которому образ не соответствует.
2. `docker build` с тегом = HEAD.
3. `k3d image import` — **до** того, как тег попадёт в git: Argo CD может выкатить сразу, и поды должны найти образ.
4. Тег и имя образа в `kustomization.yaml`, коммит **только этого файла** и push.
5. Нажимает Refresh у приложения (аннотация `argocd.argoproj.io/refresh=normal`), ждёт, пока Argo CD синхронизирует **этот** коммит, потом — `rollout status` каждого сервиса. `Released:` печатается, когда новая версия работает в кластере, а не когда коммит ушёл на GitHub.

```powershell
.\deploy\release.ps1 -Services payments-api
.\deploy\release.ps1 -Services payments-api,ledger-service
```

Выкатка идёт под всем, что настроено на этапе 2: readiness, пауза `preStop`, PDB.

## Что проверено

| Демонстрация | Результат |
|---|---|
| Изменение через git: `maxReplicas` HPA 4 → 3, push | Через Refresh — `MAXPODS 3` в кластере |
| Откат: `git revert` того коммита, push | `MAXPODS 4`; в истории Argo CD обе синхронизации с коммитами |
| Дрейф: `kubectl scale deployment/redis --replicas=0` | `selfHeal` возвращает одну реплику |
| Релиз скриптом: `payments-api`, затем `ledger-service` | Поды на `payments-api:d8882dc86ba0` и `ledger-service:c1ae1c4b9a25`. Скрипт дождался синхронизации коммита и выкатки |
| Первый релиз через CI | Тесты зелёные, `plan` выбрал ledger-service (менялся общий `src/Platform`), bank-emulator и antifraud (тег `dev`), payments-api — актуален. Три образа в ghcr.io, коммит бота, через несколько минут поды на `ghcr.io/zr-roman/…:f63d36eaa6d7` |

Тег — это версия исходников, а не содержимое образа: код Payments.Api между `:dev` и `:d8882dc86ba0` не менялся, и образ получил тот же sha256 — сборка воспроизводима, Docker взял всё из кэша. Поды всё равно перезапустились: для Kubernetes сменилось имя образа в спецификации.

## Чему научили ошибки

- **`git commit -am` закоммитил чужое.** Ключ `-a` берёт все изменённые файлы — так в коммит «HPA до 3 реплик» попала незаконченная работа над отменой авторизации в `bank.go`, а `git revert` того коммита убрал её и из рабочей копии. Работа восстановлена из коммита, но вывод — коммитить явный список файлов. Поэтому `release.ps1` коммитит `git commit -- deploy/k8s/kustomization.yaml`, что бы ни лежало в рабочей копии.
- **`rollout status` сразу после push отвечает про прошлую выкатку.** Argo CD ещё не видел коммит — отсюда ожидание синхронизации конкретной ревизии в скрипте.
- **PowerShell: результат цикла — всё, что он вывел.** Лог `docker build` оказался в списке образов, а один образ без `@(...)` — строкой, которую `@images` передал в k3d по буквам. Лог — через `Out-Host`, список — всегда массив.
- **CI нашёл нестабильный тест.** Тест квоты мерчанта ждал 250 мс, а локальное ведро лимитера пополняется по таймеру раз в 100 мс: в паузу могло попасть пополнение только за 150 мс. На ноутбуке тест проходил, на раннере — нет. Теперь пауза 400 мс, с объяснением в тесте.

## Что на стенде упрощено

| На стенде | В продакшене |
|---|---|
| Бот коммитит тег прямо в `main`, ветка не защищена | Защищённая ветка: тег приходит pull request'ом, который проверяет и сливает человек или правило |
| Код и манифесты в одном репозитории | Манифесты в отдельном репозитории: история выкаток не смешана с историей кода, права на выкатку — отдельно от прав на код |
| Sealed Secrets, ключ контроллера сохраняется руками | External Secrets с хранилищем (Vault, облачный Secrets Manager): в git — только ссылка, ротация и аудит доступа — в хранилище |
| Одна ветка, одно окружение | Отдельные пути или репозитории для окружений, продвижение версии из staging в prod через git |
| `admin` с начальным паролем | SSO через dex и RBAC проектов Argo CD |
